
## 二、Token 消耗冗余环节识别

### 2.1 SKILL.md 中的冗余

#### 冗余点 1：通用规则与规则文件的重复
- **位置**：SKILL.md "General Review Rules" 部分（约 60 行）
- **问题**：安全、性能、代码质量、测试四大类通用规则，与 security-rule.md、error-handling-rule.md 等内容大量重叠
- **影响**：每次审查都加载 SKILL.md（含通用规则），即使 Checklist 已路由到专用规则文件，通用规则仍被当作"兜底"重复检查
- **预估冗余 Token**：~1500 tokens/次审查

#### 冗余点 2：过度详细的否定条件说明
- **位置**：SKILL.md "Do NOT use this skill when" 部分（约 40 行）
- **问题**：每次审查都需要重新判断适用性，但这些排除条件在实际使用中几乎不会触发误用
- **影响**：浪费 ~500 tokens/次
- **预估冗余 Token**：~500 tokens/次审查

#### 冗余点 3：Checklist 中的路径硬编码引用
- **位置**：SKILL.md Checklist 部分（约 35 行）
- **问题**：Checklist 中直接引用了 services/api/src/routes/ 等具体路径，而这些路径已在 review-config.md 中定义
- **影响**：规则文件应从配置读取而非在 SKILL.md 中重复声明
- **预估冗余 Token**：~300 tokens/次

### 2.2 规则文件中的冗余

#### 冗余点 4：Bad/Good 代码示例过大
- **分布**：每个规则都包含 Bad 和 Good 两个代码示例
- **问题**：对于经验丰富的开发者，Bad/Good 示例提供了大量上下文但实际审查时只需要规则描述本身
- **影响**：9 个规则文件 × 平均每个 ~100 行 × ~80 tokens/行 ≈ 72,000 tokens 的规则文件总大小，其中示例代码占 ~40%
- **预估冗余 Token**：~5000-8000 tokens/次（取决于加载哪些规则文件）

#### 冗余点 5：规则描述中的重复解释
- **问题**：同一概念（如"路径遍历防护"）在 security-rule.md、filesystem-vault-rule.md、review-config.md 三个文件中分别描述
- **影响**：每次审查可能同时加载这三个文件，导致相同语义被重复理解
- **预估冗余 Token**：~1000 tokens/次

### 2.3 交互流程中的冗余

#### 冗余点 6：无参数询问但全量加载规则
- **问题**：当前流程没有参数询问步骤（这是优点），但也意味着无论审查什么代码，都会尝试匹配所有 Checklist 规则
- **影响**：即使只审查一个 SSE 路由，也会读取 security-rule.md、error-handling-rule.md 等不相关的规则文件
- **预估冗余 Token**：~3000-5000 tokens/次

#### 冗余点 7：输出模板过于固定
- **位置**：SKILL.md "Required Output Format" 部分（约 60 行）
- **问题**：模板定义了 Critical/Suggestions/Nits 三级结构，但大多数简单审查只产生 1-2 个问题，却仍需套用完整模板
- **影响**：模板描述占用 ~800 tokens，且引导模型输出冗长的分级结构
- **预估冗余 Token**：~400 tokens/次（输出端）

### 2.4 Token 消耗估算

| 环节 | 单次审查 Token 消耗 | 占比 |
|------|---------------------|------|
| SKILL.md（含通用规则+排除条件+Checklist） | ~2500 | 15% |
| review-config.md | ~2000 | 12% |
| 规则文件（平均 3-4 个） | ~8000 | 48% |
| 输出模板描述 | ~800 | 5% |
| 上下文管理（代码读取+分析） | ~3000 | 18% |
| **总计** | **~16,300** | **100%** |
